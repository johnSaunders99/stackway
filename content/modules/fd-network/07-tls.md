## 收到文件，不代表送件人的身分已經核對

你向文件網站索取說明，最在意的不只是「有沒有字回來」。如果有人能在途中讀取內容或偷偷換掉一段指令，即使整頁排版看起來正確也沒有用。傳輸層安全性 (TLS) 保護通訊的過程；HTTPS 是在這種保護下交換 HTTP 訊息。它解決的是你和哪個服務交談、途中內容能否被偷看或無聲地改動，不是替文章打品質分數。

## 連線身分與使用者身分

建立受保護的連線時，雙方協商保護資料的方式。一般網站提供數位憑證 (certificate)，並在交握 (handshake) 中證明持有對應的私密金鑰。瀏覽器會檢查憑證的信任鏈、有效期間，以及憑證是否適用於你要求的主機名稱。一般網站的憑證不是拿來直接加密整篇文章，而是協助建立受信任的交握。驗證通過後，雙方使用協商出的金鑰保護往來資料；旁觀者不能只憑看到傳輸就讀出正文，竄改也不能假裝成原本的有效訊息。

這與登入不同。就算沒登入，你也可以透過 HTTPS 讀公開文章；登入是應用程式確認「你是誰」，授權則決定「你可以做什麼」。反過來，一個有問題的網站也可能為自己的名稱取得有效憑證。憑證驗證通過，並不表示網站的每一個承諾都可信，更不表示網站有權代表名稱相似的另一個組織。

## 範例：留下 2 項不同的證據

從本課延伸資源打開 MDN，檢查網址列開頭的協定與完整主機名稱。用網址列旁的網站資訊按鈕檢視連線與憑證資訊；瀏覽器版本不同，入口不一定畫成鎖頭。記下憑證適用的主機或符合該主機的名稱範圍，不必抄整串指紋，也不要在任何頁面輸入登入資料。

在 Windows 的練習資料夾開 PowerShell，以下對同一份公開說明只取標頭，不用建立檔案。macOS 或 Linux 終端機將 `curl.exe` 改為 `curl`。需要網路；保留工具預設的憑證驗證，不要加入略過驗證的參數。

```powershell
curl.exe -I https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Transport_Layer_Security
```

成功時你會看見 HTTP 狀態與標頭，而不會看到文章本文。用兩行紀錄把觀察分開：「瀏覽器接受這次連線的憑證」、「命令列收到這個狀態」。若結果不同，記下工具、時間與原始警告；兩個工具可能用不同的信任設定。一個成功不能自動證明另一個的警告沒有意義。若當下無法連網，在筆記改用這個明示的練習案例：「工具顯示主機名稱不符，沒有 HTTP 狀態」。此時能報告的是身分驗證未通過，不是文件回了 404；把它標為案例，不要填成實測。

## 常見錯誤

遇到憑證警告就先按繼續，等同跳過「另一端真是這個名稱嗎」的檢查。先停止輸入資料，核對完整網址、裝置時間，必要時向服務維護方確認。過期、名稱不符和無法建立信任鏈是不同線索，不能只看警告顏色就斷言有人攔截。

## 小結

判讀安全連線要問三句：「我原本要找誰？工具是否信任對方提供的身分證明？這和我有沒有登入有什麼關係？」最後一句通常會把你帶回應用程式，而非帶回憑證。
