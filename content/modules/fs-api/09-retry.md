## 為什麼要學：沒有收到回應，訂單可能已經成立
你按下送出，畫面等了很久才顯示逾時。這只能證明回應沒有及時抵達，不能證明伺服器沒有完成工作。若每按一次就建立一張新訂單，重試反而把偶發的連線問題變成真實的重複紀錄。冪等性（idempotency）討論的是重複執行同一意圖後，預期的效果是否和只執行一次相同，不是要求每次連線的時間或標頭完全相同。

## 核心概念：辨認一次意圖，而不是辨認一次連線
用戶端在第一次送出前為這次操作產生冪等鍵（idempotency key），遇到不確定結果時重用原鍵；如果使用者真的要再下一張相同的訂單，則產生新鍵。伺服器在已驗證的主體與操作範圍內，記下鍵、請求參數與已完成的結果。查到同鍵同內容就重播結果；同鍵卻改內容則依契約拒絕，避免讓兩件不同的事共用一張收據。

鍵不應只用商品名稱或總金額。兩次合法購買有可能內容完全相同，而同一次操作有可能跨越重新整理。停用按鈕能減少連按，無法讓外部送達次數變得可靠。重試也不是對所有錯誤的通用處方：欄位有誤應先修正，不能期待原封不動重送後會突然通過。

## 範例：第 2 次送出，不增加第 2 筆
在 `api-notes` 新增 `retry.mjs`，用 `node retry.mjs` 執行。本例只有一個固定主體、一條建立路由及單一程序，請求依序處理；用一個字串商品代替複雜內容，讓你看得清楚哪一行產生副作用。
```js
const results = new Map(), orders = [];
function submit(key, item) {
  const old = results.get(key);
  if (old) return old.item === item ? old.result : { status: 409 };
  const id = orders.length + 1;
  orders.push({ id, item });
  const result = { status: 201, id };
  results.set(key, { item, result });
  return result;
}
for (const [key, item] of [['k1','pen'], ['k1','pen'], ['k1','pad'], ['k2','pen']])
  console.log(submit(key, item), 'count', orders.length);
```
前兩筆應有相同編號及筆數，表示不是單純顯示了兩次「成功」。第三筆的 409 是這個服務約定的衝突，不覆蓋舊收據；最後一筆即使商品相同，也因為是新的意圖而合法新增。請逐筆比對資料筆數，僅比對回應文字看不出是否真的做了兩次。

### 用收據而不是回應時間辨認重播
將第一次與第二次的輸出放在一起，遮住請求到達的時刻。兩張收據都指向同一編號，資料中也只有那一筆；這才支持「同一次建立」的結論。若只看到兩次都很快或兩次都很慢，對資料是否重複其實沒有任何證明力。

## 常見錯誤
如果兩個工作程序同時查到「鍵不存在」，各自新增後才存結果，記憶體範例就不再成立。正式系統需要持久化的唯一條件，以及把占用鍵、建立訂單、保存結果放進可原子提交的設計；外部付款之類的副作用還要有對應的服務契約，不能靠本機交易包辦。另要公告保存期限，過期後同鍵不一定還能重播。

## 小結
把「回應遺失」和「訂單不存在」分開想，再用鍵、原請求與收據把同一次意圖接回來。真正要觀察的是副作用次數，不是畫面跳了幾次通知。
