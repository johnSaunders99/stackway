## 為什麼要學：主機換了，封面最好別跟著消失

應用主機可以重新建一台，讀者上傳的原稿卻不一定還有第二份。物件儲存（object storage）讓應用用完整名稱讀寫一份內容，不必先把磁碟掛進主機的檔案系統。Amazon S3 的儲存貯體（bucket）容納物件（object），每個物件以鍵（key）識別。換掉運算主機，只要保留對應與必要權限，就能找到相同內容。

## 核心概念：斜線方便分類，不是磁碟目錄

鍵可以是 `covers/7/front.png`；`covers/` 是前綴（prefix），`front.png` 只是最後一段。另一個前綴也可以有相同的末段，因此資料庫應存完整鍵及所屬貯體，必要時還要記版本識別碼。保留私有設定，應用受理請求時先查是否能看這本書，再由有權角色讀物件；「換主機找不到」通常要檢查對應和角色，不是把貯體改成公開。

啟用版本控制（versioning）後，同一鍵的覆寫會產生新版本。一般不指定版本的刪除會放上刪除標記（delete marker），一般讀取不再呈現舊內容，但不等於舊版都已清除。生命週期規則（lifecycle rule）可依條件轉換儲存類別或讓版本到期；目前版本和非目前版本要分別規劃。版本控制保留救援機會，但保留的內容仍會占用儲存。

## 範例：把一個鍵的歷史攤開來看

在 `C:\dev\stackway-lab\aws` 存 `objects.py`，執行 `py objects.py`；macOS／Linux 用 `python3 objects.py`。以顏色字串代替圖片，空值只在這個模型中代表刪除標記。這裡不建立真貯體，也沒有模擬物件權限或 AWS 產生版本編號的方式。

```python
bucket = {"covers/7/front.png": []}
history = bucket["covers/7/front.png"]
for value in ["blue", "green", None]:
    history.append(value)
    current = history[-1]
    print("latest", current if current is not None else "not found",
          "version-1", history[0])
```

拿紙蓋住最後的標記，看見底下的綠色，不表示它自動又成為現行版。若目標是恢復藍色，可把已核對正確的舊內容當成新版本寫回，並重新驗收不指定版本的普通讀取。若舊版已被永久刪除，或覆蓋前根本沒有版本保存，就不能依賴這條救援路徑。

### 用 2 種目錄問題拆開保管與清理

若讀者問「我的封面不見了」，處理的人先看該鍵的現行狀態與版本清單，找出哪一次更新之後看不見。若帳務問「封面都刪完了，為什麼容量還在」，同一份清單要看的卻是哪些非目前版本仍占空間、各自受哪條期限管理。前者可能需要把一份舊內容恢復成現行，後者可能需要等保留期結束。兩個問題面對同一個刪除標記，正確下一步並不相同；不能為了讓一般清單變空就清光能救回原稿的版本。

## 常見錯誤與小結

列出目前物件數為 0，不足以證明貯體沒有保留成本；還要檢查非目前版本與適用保留規則。反過來，為節省費用而立即清掉所有舊版，也可能使誤覆寫來不及發現。先定義多久內應能找回，依此決定版本期限，然後拿一份測試原稿演練還原，而不是只驗證「上傳成功」。
