## 為什麼要學：畫面不動，不一定是算不動

按了「分析檔案」，頁面一直轉圈。可能是資料還沒送到，也可能是資料早到了，程式正忙著算。輸入輸出（input/output，I/O）是與檔案、網路等交換資料；計算則是用已取得的資料做運算。兩者都會花時間，解法卻不同：縮短迴圈不會縮短等待對方回覆的時間。

## 核心概念：誰得等，誰可以先走？

阻塞（blocking）表示呼叫的那條執行路徑要等操作有結果，才有辦法繼續下一行。非阻塞（non-blocking）操作若還不能進行，會把控制權交還，讓呼叫者做別的事，而不是就地等待。非同步（asynchronous）介面則把「開始」和「收結果」拆開；它可以由背景工作執行阻塞式呼叫來實作，兩個詞不是同義詞。

以下用一個有意安排的延遲做對照，不會真的拖慢你的磁碟。執行器（executor）替主線安排工作，回傳的 `Future` 像取件單。拿到單子能先去備料，回到窗口領件時如果還沒好，仍然要等。之後在瀏覽器的[〈回呼與非同步結果〉](#/lesson/fs-browser-03-callbacks)會用另一種方式把完成後的工作交代清楚。

## 範例：分段計時，不把睡眠算成磁碟速度

在練習區的全新 `io-lab` 資料夾建立 `timing.py`，從這裡執行 `py timing.py`；其他系統用 `python3 timing.py`。檔案只在此練習中建立與改寫。

```python
from pathlib import Path
from time import perf_counter, sleep
from concurrent.futures import ThreadPoolExecutor

p = Path("sample.bin")
p.write_bytes(b"x" * 65536)
def get_data():
    start = perf_counter()
    sleep(0.15)
    data = p.read_bytes()
    return data, perf_counter() - start

with ThreadPoolExecutor(max_workers=1) as pool:
    ticket = pool.submit(get_data)
    print("preparing report")
    data, read_s = ticket.result()
start = perf_counter()
total = 0
for _ in range(40):
    total += sum(data)
print(len(data), total, "wait+read", read_s, "compute", perf_counter() - start)
```

第一段從背景工作開始量到讀完，包含刻意加上的等待；第二段只量手上已有資料之後的加總。若把重複次數加倍，預測改變的主要是第二段，不是第一段。測試時保持檔案大小不變；若兩個地方一起改，即使總時間變長，也無法判斷是哪個階段造成。

### 真正的非阻塞讀取是什麼樣子？

在同一資料夾另存 `probe.py`，執行 `py probe.py`（其他系統用 `python3 probe.py`）。通訊端（socket）是程式收送資料的端點；這裡配成已連通的一對，不對外開放服務。對端還沒送東西，接收端卻不必等到有資料才能做下一件事。

```python
import socket

reader, writer = socket.socketpair()
with reader, writer:
    reader.setblocking(False)
    try:
        reader.recv(1)
    except BlockingIOError:
        print("not ready")
    print("can continue")
```

這裡的「還不能讀」不是讀到空檔，也不是工作已完成，而是可以等就緒通知再試。不要在無休止的迴圈中立即重試，否則會把原本的等待變成浪費處理器的忙等。與前面的背景讀檔對照，這次沒有工作者代替主線等待。

### 如何選下一次量測

假設讀取階段總是花約 1/6 秒，計算階段卻隨重複次數大幅增加。若需求是讓整份報表早點完成，就先減少對相同資料的重算；若需求是按下按鈕後立刻顯示進度，則該查主線是不是過早領取結果。兩種改法可以來自同一組量測，目標卻不同。也可以先移除刻意加入的等待，只保留相同檔案再跑一次。這個對照能顯示先前的數字有多少來自模擬條件，不能拿來預測使用者在慢速網路磁碟上會花幾秒。

## 常見錯誤

重讀小檔可能直接命中作業系統快取，不一定每次都接觸實體磁碟。只憑一次讀取耗時不能斷定磁碟性能。另一個陷阱是送出背景工作後馬上取結果，雖然用了非同步介面，主線仍會停在取件處；觀察式子要看在哪一行等，而不是看有沒有用特定函式名稱。

## 小結

先切出等待與計算的界線，再決定要少讀、少算，還是讓呼叫者在等待期間保持可用。這個小實驗能驗證流程與計時位置，不是硬體效能排行榜。
