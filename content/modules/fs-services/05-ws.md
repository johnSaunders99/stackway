## 為什麼要學：不開頁面，工作還會完成嗎？

預覽圖在工作者上算，瀏覽器只是在等結果。輪詢（polling）讓頁面定時問伺服器「好了嗎」，簡單但可能反覆收到一樣的答案。WebSocket 是可保持開啟的雙向連線；建立後兩邊都能主動傳訊。工作者完成時，由服務通知頁面，比等下一輪詢問來得即時。對偶爾看一次的進度，輪詢反而可能是較容易維護的選擇。

## 核心概念：事件帶消息，狀態給答案

瀏覽器用 `new WebSocket(...)` 建立連線，`open` 才表示可以傳送訂閱，`message` 接受事件，`close` 表示這條連線已結束。應用程式要驗證訂閱者能否讀這項工作。連上傳輸通道和成功訂閱某個工作是兩件事，最好有訂閱確認；連線中斷也不等於背景工作失敗。不要在關閉事件裡替使用者自動再排一份工作。

想像工作從排隊、處理中到完成，每次狀態改變都附上由服務遞增的版本。持久化的狀態可透過一般查詢重新取得。重連流程先恢復訂閱，確認生效後再查當下狀態，避免查完才開始訂閱而漏掉中間的更新。這時查詢結果與即時事件誰先到都可能，只套用同一工作較新的版本，重複的通知也不需要重畫。

## 範例：讓第 2 版故意晚於第 3 版

在 `C:\dev\stackway-lab\services` 建立 `status.mjs`，在終端機執行 `node status.mjs`。這段不連網，重播的是畫面收到事件後最容易寫錯的判斷。`source` 表示訊息從哪裡來，不決定哪一種來源可以無條件覆蓋別人。

```js
let view = {job: "preview-7", version: 0, state: "unknown"};
function receive(source, item) {
  if (item.job === view.job && item.version > view.version) view = item;
  console.log(source, view.version, view.state);
}
receive("socket", {job:"preview-7", version:1, state:"queued"});
console.log("offline; reconnect and confirm subscription");
receive("snapshot", {job:"preview-7", version:3, state:"done"});
receive("socket", {job:"preview-7", version:2, state:"working"});
```

把接收處改成「只要來就更新」，最後一行會從已完成倒退成處理中。這不一定是同一條連線自己把訊息次序打亂：一次普通查詢的回應、不同連線上的通知與重新訂閱，原本就不是同一條傳輸序列。版本要由服務產生，不能拿畫面收到訊息時的本機時間取代。

### 一筆通知都沒收到時怎麼辦？

考慮另一條時間線：頁面關閉前只見排隊，工作在夜裡完成，隔天開頁時伺服器不會再產生第二次「剛完成」事件。即使此刻的連線完全健康，坐等下一則通知也只會一直顯示排隊。把開頁與重連看作相同的同步問題，先讓往後的更新接得到，再取得現在的答案。若服務沒有版本或可重讀的狀態，就不能光靠前端排序補出錯過的事；這時要先補足服務契約，或把介面明確標為最後一次收到的消息。

## 常見錯誤與小結

一直轉動的圖示無法區分還在計算、正在重連或查不到工作。暫時離線時保留最後確認的狀態並標註可能過時，重連失敗可以讓讀者手動更新。真正驗收的不只是連線有沒有亮起來，而是漏過一次通知後，讀者仍能找到正確結果。
